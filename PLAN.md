# Пошаговый план реализации Bill Bot (Alligator EMA + подтверждённые фракталы) для Hyperliquid

## Реализовано
- Шаг 1: создан каркас проекта (Python 3.13) и инфраструктура запуска (Docker + защищённый Redis).
  - Добавлены файлы инфраструктуры:
    - `requirements.txt` (зависимости: aiohttp, redis)
    - `Dockerfile` (сборка образа, запуск `python -m bill_bot.main`)
    - `docker-compose.yml` (сервисы `bot` и `redis`)
    - `.env.example` (пример переменных окружения, включая `REDIS_PASSWORD`)
  - Защита Redis:
    - Redis стартует с `--requirepass ${REDIS_PASSWORD}`
    - Подключение бота к Redis идёт по URL с паролем (если пароль задан)
  - Каркас приложения:
    - `bill_bot/` пакет
    - `bill_bot/core/config.py` (чтение env)
    - `bill_bot/core/redis_client.py` (инициализация Redis-клиента)
    - `bill_bot/main.py` (bootstrap: Redis PING и дальнейший цикл ожидания; dry-run)
  - Верификация:
    - `python -m compileall bill_bot` проходит без ошибок

- Шаг 2: DataFeed (MVP) — догрузка истории 15m и фиксация закрытых свечей.
  - Реализован клиент Hyperliquid `candleSnapshot` через POST `/info`.
  - При старте по `PAIRS`:
    - догружается история и сохраняются последние `HISTORY_BARS` закрытых свечей в Redis
    - ключи: `candles:<pair>:15m` (JSON-массив), `candles_meta:<pair>_15m` (count, ts_from, ts_to)
  - Реализован polling закрытия свечей:
    - раз в `POLL_SECONDS` запрашивается небольшой диапазон последних свечей
    - при появлении новой закрытой свечи она добавляется в окно и логируется как `New closed candle`

- Шаг 3: Indicators (MVP) — Alligator EMA(13/8/5) и определение “сон/не сон” по SpreadLines.
  - Добавлен расчёт EMA и линий Alligator по Close: Jaw=13, Teeth=8, Lips=5.
  - Добавлен SpreadLines = max(Jaw,Teeth,Lips) - min(Jaw,Teeth,Lips).
  - Добавлен критерий сна:
    - берём медиану SpreadLines по окну `SLEEP_WINDOW` (по умолчанию 20)
    - сравниваем с порогом `SLEEP_K * last_close` (по умолчанию 0.001)
  - Сохраняем последнее состояние индикаторов в Redis:
    - ключ `ind:last:<pair>:15m` (JSON: jaw/teeth/lips/spread/sleep/параметры сна)
  - В логи пишется строка `Alligator: ... sleep=... med_spread=...`

- Шаг 4: FractalDetector (MVP) — подтверждённые кластера (фракталы) по окну 5 свечей.
  - Добавлен детектор подтверждённых фракталов:
    - HIGH: High[i] выше High[i-1], High[i-2], High[i+1], High[i+2]
    - LOW: Low[i] ниже Low[i-1], Low[i-2], Low[i+1], Low[i+2]
    - подтверждение происходит при наличии 2 следующих свечей (в realtime проверяем центр = len(window)-3)
  - Для каждого фрактала сохраняем: kind, t (время центра), price (high/low), close свечи центра, teeth на свече центра.
  - Хранение в Redis:
    - ключ `fractals:<pair>:15m` (JSON-список, ограничение `FRACTALS_MAX`)
  - В логи пишется строка `Fractal confirmed: ...`

- Шаг 5: StrategyEngine (MVP) — генерация “кандидата сигнала” по правилам Bill Williams.
  - Условия кандидата:
    - sleep=true (из SpreadLines)
    - LONG: последний HIGH-фрактал, у которого close кластера > teeth кластера
    - SHORT: последний LOW-фрактал, у которого close кластера < teeth кластера
  - Вход:
    - stop-market trigger = cluster_price ± 1 tick (tick получаем из API Hyperliquid по `szDecimals` и правилам tick size)
  - SL:
    - LONG: ближайший LOW-фрактал до HIGH-кластера, у которого close < teeth (на свече кластера)
    - SHORT: ближайший HIGH-фрактал до LOW-кластера, у которого close > teeth (на свече кластера)
  - TP:
    - RR = 1 : 1.5
  - Хранение кандидата в Redis:
    - `signal_candidate:last:<pair>:15m`
  - В логи пишется строка `Signal candidate: ...`

- Шаг 6: Tick size из API (улучшение шага 5).
  - Бот получает `szDecimals` инструмента через Hyperliquid `/info` type=`meta`.
  - Tick size вычисляется динамически от цены кластера по правилам Hyperliquid:
    - ограничение по числу знаков после запятой: `MAX_DECIMALS - szDecimals` (для perps `MAX_DECIMALS=6`)
    - ограничение по 5 значащим цифрам
    - итоговый tick = max(tick_by_decimals, tick_by_sigfig)
  - `TICK_SIZE` остаётся как fallback, если API недоступен или инструмент не найден.

- Шаг 7: ExecutionDryRun (MVP) — виртуальные ордера/позиции и P&L.
  - После появления `signal_candidate:last:<pair>:15m` бот может поставить dry-run ордер, если нет активного ордера/позиции.
  - Размер позиции:
    - пока берём из env: `VIRTUAL_EQUITY` и `RISK_PCT`
    - qty = (equity * risk_pct/100) / abs(entry - SL)
  - Исполнение:
    - LONG: ордер срабатывает, если high свечи >= trigger
    - SHORT: ордер срабатывает, если low свечи <= trigger
    - entry price в MVP = trigger
  - Сопровождение:
    - SL/TP проверяются по диапазону свечи
    - если SL и TP в одной свече: в MVP считаем, что сработал SL (консервативно)
  - Хранение в Redis:
    - `state:<pair>:15m` (ord/pos/last_trade)
    - `pnl:<pair>:15m` (unrealized/realized)
  - В логи пишутся события: `Dry-run order placed`, `Dry-run event: position_opened/position_closed`

## 0) Зафиксированные требования
- Рынок: Hyperliquid.
- TF: 15m.
- Alligator:
  - Jaw = EMA(Close, 13) (синий)
  - Teeth = EMA(Close, 8) (красный)
  - Lips = EMA(Close, 5) (зелёный)
- Кластера (фракталы, только подтверждённые):
  - LONG-кластер: High[i] > High[i-1], High[i-2], High[i+1], High[i+2]
  - SHORT-кластер: Low[i] < Low[i-1], Low[i-2], Low[i+1], Low[i+2]
  - Используем только подтверждённые фракталы (задержка 2 свечи).
- Сетап LONG:
  - Аллигатор “спит” на последних N свечах (для старта N=20).
  - Появился подтверждённый LONG-кластер, и свеча кластера закрылась выше Teeth (красной).
  - Вход: stop-market на пробой уровня кластера + 1 tick.
  - SL: ближайший противоположный кластер (SHORT-фрактал), при этом свеча кластера закрылась ниже Teeth.
  - TP: RR = 1 : 1.5 (TP = entry + 1.5*(entry - SL)).
- Сетап SHORT: зеркально.
- Критерий “сон” (первый вариант): SpreadLines.
- Риск: задаётся в Telegram в % от депозита.
- Режим исполнения на старте: dry-run (учёт ордеров/позиций/PNL без реальной торговли).
- Стек: Python 3.13 + Redis (защищённый) + Docker.
- Telegram UX:
  - выбор пары (multi-select) и TF
  - запуск отслеживания выбранных пар (догрузка 100 бар + обработка каждой закрытой 15m свечи)
  - просмотр отслеживаемых пар (список + открытые позиции + P&L)
  - отслеживание P&L (реализованный и нереализованный)
  - просмотр графика выбранной пары с Alligator + кластерами
- ML/LM: анализ предыдущих сделок и коррекция последующих (адаптация параметров), без изменения базовой логики вход/SL/TP “на лету”.

## 1) Целевой результат (MVP)
MVP считается готовым, когда бот:
- стабильно получает 15m свечи по выбранным парам;
- детектит подтверждённые фракталы, рассчитывает Alligator EMA 13/8/5;
- определяет “сон”, генерирует сигналы, выставляет dry-run entry/SL/TP;
- ведёт позиции и P&L (реализованный/нереализованный) в разрезе пар;
- отдаёт в Telegram: управление подписками, статус, P&L, график с разметкой.

## 2) Архитектура (модули)
Минимальный состав модулей:
- DataFeed
  - подписка на данные Hyperliquid
  - сбор/обновление 15m свечей
  - начальная догрузка истории (100 бар)
- Indicators
  - EMA(13/8/5) по Close
  - метрика SpreadLines
- FractalDetector
  - выявление/подтверждение фракталов (5 свечей)
  - хранение списка последних подтверждённых кластеров
- StrategyEngine
  - sleep-condition
  - правила входа/SL/TP
  - генерация торгового намерения (intent)
- ExecutionDryRun
  - симуляция stop-market ордера (trigger=cluster±tick)
  - логика “ордер сработал на свече”
  - сопровождение позиции, закрытие по SL/TP
- Portfolio / PnL
  - учёт позиции (side, entry, size, SL, TP)
  - unrealized P&L по mark price
  - realized P&L при закрытии
- Storage (Redis)
  - свечи, кластера, состояние ордеров/позиций, журнал сделок
- Telegram UI
  - выбор пар, TF
  - запуск/остановка отслеживания
  - статус, позиции, P&L
  - запрос графика по паре
- ML Tuner (позже, но закладываем интерфейсы)
  - сбор истории сделок
  - расчёт метрик и подбор параметров
  - применение параметров через конфиг-слой

## 3) Redis (защищённый) + Docker
Шаги:
1) Docker-compose: сервисы bot + redis.
2) Защита Redis:
   - пароль (requirepass через env)
   - не публиковать порт наружу без необходимости (либо ограничить bind/Firewall)
   - отдельная docker network
3) Хранилища/ключи (черновая схема):
   - `candles:<pair>:15m` (последние 100–300 свечей)
   - `fractals:<pair>:15m` (последние подтверждённые фракталы)
   - `state:<pair>:15m` (активный ордер/позиция)
   - `pnl:<pair>` (агрегаты P&L)
   - `trades:<pair>` (журнал закрытых сделок)
   - `subs:<user_id>` (выбранные пары, TF, risk%)

Проверка готовности шага:
- Redis стартует с паролем, бот подключается по password.
- У Redis нет “лишней” публикации портов наружу (если не требуется).

## 4) DataFeed: свечи 15m (история 100 бар + realtime)
Шаги:
1) Выбор источника:
   - получать 15m свечи напрямую (если API позволяет), иначе строить из более мелких.
2) При старте подписки:
   - загрузить последние 100 15m баров.
3) Realtime:
   - по закрытию каждой 15m свечи обновлять хранилище и запускать расчёты.

Проверка готовности шага:
- Для каждой выбранной пары есть стабильный поток закрытых 15m свечей.
- В Redis всегда поддерживается окно минимум 100 свечей.

## 5) Indicators: Alligator EMA + SpreadLines (сон)
Шаги:
1) Реализовать расчёт EMA(13/8/5) по Close.
2) Реализовать SpreadLines:
   - `spread = max(jaw, teeth, lips) - min(jaw, teeth, lips)`
3) Sleep-condition:
   - на последних N свечах (N=20) спред “маленький”
   - первый вариант порога:
     - `median(spread последние N) < k * price`, где price = last_close
     - k задаём конфигом и подбираем в ходе первых тестов

Проверка готовности шага:
- Значения EMA и spread воспроизводимы на одном и том же наборе свечей.
- В логах видно sleep=true/false с метрикой.

## 6) FractalDetector: подтверждённые кластера
Шаги:
1) Реализовать детектор фракталов по окну 5 свечей.
2) Учесть подтверждение:
   - фрактал на i фиксируем только когда доступны i+1 и i+2
3) Хранить:
   - список последних подтверждённых HIGH-фракталов и LOW-фракталов
   - индекс/время свечи центра фрактала

Проверка готовности шага:
- В логах видно момент подтверждения фрактала.
- Фрактал появляется с задержкой ровно 2 свечи.

## 7) StrategyEngine: правила входа/SL/TP
Шаги:
1) LONG:
   - sleep=true на последних N
   - есть подтверждённый HIGH-фрактал, и close свечи фрактала > Teeth (на свече фрактала)
   - entry trigger = fractal_high + 1 tick
2) SL:
   - выбрать ближайший подтверждённый противоположный LOW-фрактал
   - фильтр: close свечи этого кластера < Teeth (на свече этого кластера)
3) TP:
   - RR 1:1.5
4) SHORT: зеркально.
5) Дедуп:
   - если уже есть активный ордер/позиция по паре — не создавать новый.

Проверка готовности шага:
- На синтетическом наборе свечей стратегия выдаёт ожидаемый intent (entry/SL/TP).

## 8) ExecutionDryRun: симуляция stop-market и сопровождение
Шаги:
1) Постановка entry-ордера (dry-run state):
   - тип: stop-market
   - trigger=fractal±tick
2) Исполнение:
   - на каждой новой закрытой свече проверять, был ли пробой trigger:
     - для LONG: high >= trigger
     - для SHORT: low <= trigger
   - при “срабатывании” фиксировать entry price (вариант MVP: trigger).
3) Сопровождение:
   - проверять SL/TP на каждой новой свече
   - учитывать конфликт “в одной свече и SL и TP” (правило приоритета фиксируем заранее)
4) Запись сделки в журнал + обновление P&L.

Проверка готовности шага:
- Для тестового кейса позиция открывается/закрывается, P&L обновляется.

## 9) P&L: реализованный и нереализованный
Шаги:
1) Unrealized:
   - расчёт от mark/last price.
2) Realized:
   - фиксировать при закрытии сделки.
3) Агрегация:
   - по паре и по пользователю (если мультипользовательский режим).

Проверка готовности шага:
- Команды Telegram показывают корректные цифры для открытой позиции и после закрытия.

## 10) Telegram UX (кнопки и сценарии)
Шаги:
1) Меню:
   - выбор пары (multi-select)
   - выбор TF (в MVP фиксируем 15m, но UI оставляем)
   - ввод risk% (валидация)
2) “Запуск отслеживания”:
   - догрузка 100 баров
   - старт фоновой задачи по паре
3) “Отслеживаемые пары”:
   - список + состояние (нет ордера/есть ордер/в позиции)
   - P&L по каждой паре
4) “P&L”:
   - общий realized/unrealized
5) “График”:
   - выбрать пару → получить картинку

Проверка готовности шага:
- Все кнопки работают без падений, состояние сохраняется между рестартами (через Redis).

## 11) График: Alligator + кластера (15m, окно 100 баров)
Шаги:
1) Генерация графика по 100 последним свечам:
   - свечи OHLC
   - линии EMA 13/8/5
   - маркеры фракталов (high/low)
2) Отправка в Telegram как изображение.

Проверка готовности шага:
- На графике корректно видны линии и отметки кластеров, масштабы читаемые.

## 12) ML/LM: анализ истории сделок и коррекция параметров (этап 2)
Цель: повышать качество сигналов не “магией”, а через адаптацию параметров.

Шаги:
1) TradeJournal:
   - сохранять фичи сетапа на входе + исход сделки.
2) Метрики:
   - winrate, expectancy, PF, maxDD, средний R, распределения по времени суток/волатильности.
3) Коррекция параметров:
   - k для sleep-condition
   - TTL (если добавим) и/или дополнительные фильтры
   - tick buffer (если понадобится)
4) Использование LM:
   - периодически формировать отчёт и просить LM объяснить паттерны + предложить изменения
   - изменения включаются только после подтверждения (в Telegram).

Проверка готовности шага:
- Есть отчёт по сделкам и механизм применения параметров без перезапуска (или с контролируемым перезапуском).
